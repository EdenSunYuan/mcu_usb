# 模块设计报告编写规范

> 每个 RTL 模块设计定稿（验证通过）后，都要写一份**独立的设计报告**，统一按本规范
> 的 **4 节结构**编写。本文件即模板，后续所有模块（`usb_rx_deserial` / `usb_tx_serial` /
> `usb_dpll_cdc` / `usb_sie` / `usb_ep_fifos` / `usb_apb_slave` / `usb_regs` …）的
> 设计报告都必须遵循，不得另起炉灶。
>
> §1–§4 管设计报告的结构；**§5–§7 管排版、文风与公众号兼容，对全仓库所有 Markdown 都适用**
> （设计报告、验证报告、`PROGRESS.md`、`CONVERSATION_LOG.md`、README）。

## 0. 命名与存放

| 产物 | 路径约定 | 生成方式 |
|------|---------|---------|
| 设计报告（Markdown 源） | `doc/XX_<模块>_design.md` | 手写（本规范模板） |
| 设计报告（Word 版） | `doc/<模块>设计报告.docx` | `tools/gen_report_docx.py`（Markdown → docx） |
| 波形截图 | `doc/fig/<模块>_<场景>.png` | `tools/render_waveform.py`（复用 `wave_debugger.py`） |
| 设计意图时序图（RTL 未落地时的过渡） | `doc/fig/<模块>_<场景>.png` | `tools/gen_tx_timing.py` 等**按设计语义**的 Python 参考模型；RTL 完成后必须换成真 VCD 截图（脚本降级为 `--check`/`--dump` 自检与旁证工具，不再出图） |
| 状态机 / 框图 | `doc/fig/<模块>_*.png` | `tools/gen_fsm_diagrams.py` / `tools/state_machine_gen.py` |

## 1. 模块介绍

**写什么**（一段话 + 要点列表，回答"这是什么、放哪、干什么"）：

1. 模块全名、在系统层次中的位置（挂在哪层、上下游是谁）；
2. 一句话功能（输入 → 输出，做什么变换）；
3. 工作时钟域与频率（如 `ref_clk` 48MHz / `pclk` 域）；
4. 核心思想/关键技术（如"16 态 DPLL 数字锁相环"）；
5. 与上下层模块的接口边界（只做位流/字节流，不做包解析……）。

**反例**：一上来就贴状态机图或代码，读者不知道这模块是干嘛的。

---

## 2. 模块设计理论和原理及方法

**写什么**（这是报告的"重头戏"，回答"为什么这么做、原理推导、具体方法"）：

按 **动机 → 理论 → 原理推导 → 实现方法** 的次序展开：

1. **设计动机 / 为什么需要它**：驱动这个设计的问题是什么（如"主机与设备晶振异步"）；
2. **理论基础**：采用的成熟理论/参考文献（如 Intel SIE DPLL 白皮书），用一两句话讲清；
3. **原理推导**：关键公式 / 数值（如 4× 过采样、8× 等效、±0.25% 容差 → 相位误差有界）；
4. **实现方法**：
   - 核心结构（状态机、计数器、移位寄存器…），配状态机图/框图；
   - 完整的状态跳转表（当前态 / 条件 / 次态 / 说明）；
   - 关键编码约定（如 `state[1]`=时钟、`state[2]`=数据）；
5. 结尾一句话点明"**为什么这个方法可综合/正确**"（如单时钟、纯组合+时序、无 `#` 延迟）。

**要点**：讲"为什么这么做"的**设计判断**，而不是罗列代码行。图和表配合文字，不能只有文字。

## 3. 模块信号列表

**写什么**（两张表，务必与实际 RTL 端口**逐位一致**）：

### 3.1 端口信号（对外接口）

统一表格：

| 端口 | 方向 | 位宽 | 说明 |
|------|------|------|------|
| `ref_clk` | in | 1 | 48MHz 参考时钟 |
| `ref_rstn` | in | 1 | 异步复位，低有效 |
| `rxdp` | in | 1 | D+ 单端（J=1, K=0） |
| `clk12m` | out | 1 | 恢复的 12MHz 时钟（寄存器输出、无毛刺） |

按 **时钟/复位 → 输入 → 输出** 分组，必要时用 `**物理侧**` / `**RX 输出**` 等分组行。

### 3.2 内部关键信号（寄存器 / 连线）

| 信号 | 类型 | 位宽 | 说明 |
|------|------|------|------|
| `stat_cur` | reg | 4 | FSM 现态（规则 7：`<名>_stat_cur`） |
| `stat_nxt` | reg | 4 | FSM 次态（组合逻辑结果） |
| `a_reg` / `b_reg` | reg | 1 | 双沿采样锁存值 |

**要求**：`localparam` 常量（状态编码等）单独列一张小表或用代码块列出。

## 4. 关键设计点描述及波形

**写什么**（逐条列出设计中的**关键点 / 难点 / 决策**，每条 = 一段说明 + 一张图）：

每个关键点一个小节，结构固定为：

1. **问题**：这个点为什么难/为什么关键；
2. **设计做法**：怎么解决的（文字 + 必要时公式/伪码）；
3. **波形/图**：一张波形截图或状态机图，**必须有 figure caption**（图号 + 一句话说明看到了什么、如何印证设计）。

典型关键点举例（CDR 的 6 个）：
- 锁存过程（C→D→5）→ 配 `cdr_lock.png`
- 左右环循环 → 配状态机图
- F/B 长 bit 绕行 → 配 `cdr_f_detour.png`
- 频率自适应（短/长 bit 相位调整）
- 恢复时钟去毛刺（`state[1]` 打一拍）
- 数据提取（`state[2]`）

**要点**：波形不是装饰，要能"用波形证明这个设计点成立"，caption 里点明"看哪个信号、什么现象、印证了什么"。图统一放在 `doc/fig/`，Markdown 报告正文里一律用**相对路径超链接**（`fig/xxx.png`）引用（见 §5 约定）。

## 5. 通用格式约定

- **标题层级**：`#` 一级（报告名）、`##` 四大节、`###` 子节，编号用 `1. 2. 3. 4.`；
- **表格**：所有列表（信号、跳转、参数、结果）用 Markdown 表格，不用长段落堆数字；
- **单元格必须短（防"显示不全"）**：单元格文字**一行放得下**为准（中文 ≤30 字 / 英文 ≤60 字符量级），
  只放一个**短语级**结论；凡是多句说明、历史沿革、代码片段、判据推导，一律**移到表格下方**的列表/段落。
  一张表只表达一个语义维度，宁可**拆成两张表**，也不把长文本塞进单元格。
  *为什么*：不少 Markdown 阅读器（含 Word / docx 导出链路）不给表格横向滚动，超长单元格会被截断，
  或把整张表撑到屏幕外 → 读者看到的就是"内容显示不全"（用户 2026-09-15 定）。
  自检：单元格 ≥120 字符就要拆；`PROGRESS.md` §2 "状态"列是**反面教材**（历史沿革挤在一格）。
- **整表要放得下一页（用户 2026-09-28 定）**：转成 Word 后一页放不下就要左右滑，也算"显示不全"。
  两条手段配合用：**先压列数**（同类列合并、表头写全，如 `connected` / `suspended` 合成一列写 `0 / 0`），
  **压不下去就降字号**——`tools/gen_report_docx.py` 按列数自动降档：≤5 列 10.5pt，6~7 列 9pt，更多 8pt。
  典型靠字号兜住的：`tx_serial_verification.md` §4.10 那张 9 列的逐拍表。
- **表格要自足（用户 2026-09-28 定）**：该进表的信息一律进表，**不许在表下再用文字补全**——
  比如把"标志位动作"整列挪到表下写三句话，读者得来回对着看，等于没写完。
  压列数的办法是合并同类列、把表头写全，不是把列删掉改写成散文。
  表下只留两类内容：表里**没有**的行为什么没有（结构不可达 / 前提不成立），以及这张表本身不讲的性质。
- **简洁优先（反啰嗦）**：先结论后论据；一段只说一件事；判据只给数值 + 阈值，推导留给设计报告。
  **同一个解释全仓库只写一处**：放在最合适的那份报告里，别处一句话引用；不要在设计报告、验证报告、
  代码注释、README 里各复述一遍。自检：任意小节砍掉一半字数，若信息没丢就该砍（用户 2026-09-15 定）。
- **文风（反 AI 腔）**：见 §6。
- **代码/伪码**：用 fenced code block（\`\`\`），标注语言（verilog / 纯文本）；
- **中英对照**：关键术语首次出现给英文（如 时钟数据恢复（CDR，Clock Data Recovery））；
- **图**：一律有 caption（图 N …），正文里用**超链接**引用、**不内嵌** `![](...)`——
  `📎 [打开…：<说明>](fig/xxx.png)`（用户 2026-09-07 定；同 `design_rpt/02_cdr_verification.md` §4.3 风格）。
  原因：部分阅读器 / 文档转换对相对路径内嵌图不渲染，超链接点击即开、天然可回退；Word 版由
  `tools/gen_report_docx.py` 在导出时才真正内嵌 PNG（见本行末约定）。
  **发公众号的文档反过来，图必须内嵌**，见 §7.1（用户 2026-10-08 定，覆盖本条）。
  **取信号要覆盖因果**：图里同时有结论信号与导致它的信号，见 `sim/common/README.md` 规则 5（用户 2026-09-21 定）；
- **引用验证报告**：§4 末尾用 `> 详细验证见 [XX_<模块>_verification.md](...)`；
- **Word 版**：内容与 Markdown 一致，用 `tools/gen_report_docx.py` 生成，内嵌 PNG。

## 6. 文风：别写成 AI 腔（2026-09-21 用户定）

要避免的主要是一件事：让读者一眼看出这是机器写的。修辞上的花架子会让人不再信任里面的数字，
而这份文档最值钱的就是数字。

标准很朴素：像跟同事口头交代一件事那样写。读者是懂行的，不用"讲明白"，要的是能快速核对。
不适用本节的只有状态速查类（`PROGRESS.md` §2 的表、`README.md` 的章节目录），那些本来就该是电报体。

### 6.1 六种腔调，见到就改

| 病症 | 长什么样（例子都出自本仓库） | 怎么改 |
|---|---|---|
| 破折号插入语 | `三根信号各差一拍 —— 正是两级延迟摊开的样子` | 拆句号或冒号，后半截多半可以直接删 |
| 强调收尾 | `bit_cnt 停在 3 一拍 —— 这就是插进去的那个 0` | 删"这就是…"。事实已经说完了，不用再敲一下桌子 |
| 对仗句 | `不是 X，而是 Y` ／ `不仅 X，更是 Y` | 说 X。真有两个并列的点，就分两句 |
| 加粗刷屏 | 每条 bullet 都长成 `**短语**：正文` | 见 §6.2 |
| 元评论 | `值得注意的是` `需要强调的是` `本质上` `由此可见` | 删 |
| 复述收尾 | 段末把刚说的再说一遍 | 删 |

这些词不是禁用，是不能当口头禅。一篇文章里 `恰好` 出现两三次很正常，有时它就是最准的词；
每段都来一次，就是腔调。

### 6.2 两条能量的线

grep 数得出来，超了就回头查。口径是**只数正文散文**：跳过标题行、表格行、代码块，
在下面这批自己写的文档上量（设计/验证报告、`PROGRESS.md`、`CLAUDE.md`、规范文件）。

| 指标 | 上限 | 现状最差 |
|---|---|---|
| 破折号 `——` | 1 处 / 千字 | 3.7（`code_rtl.md`） |
| 加粗 `**` | 6 处 / 千字 | 16.4（`intel_sie_whitepaper_notes.md`） |

`doc/usb协议解读/` 下的协议笔记是外部资料的整理，不适用本节。

加粗只留给两处：术语首次定义、必须一眼扫到的判据值（时间戳、拍数、百分比、错误数）。
不要拿它给每句话贴标签，满篇黑疙瘩等于没有重点。

### 6.3 两个改写实例

改前（`tx_serial_verification.md` §4.7）：

> `tx_active`↓ @1927145 → `tx_stat_cur` 到下一沿 @2010481 才回 `S_IDLE` → `tx_en`↓ @2093817。
> **三根信号依次相差整一拍**，正是"现态译码 + 寄存器输出"两级延迟在图上摊开的样子。

改后：

> `tx_active`↓ @1927145。下一沿 @2010481 回 `S_IDLE`，@2093817 `tx_en`↓。三根信号各差一拍：
> `tx_active` 是 TB 侧寄存器，状态迁移看它当拍的值，`tx_en` 又看当拍的状态。

去掉破折号和强调收尾，信息一点没少，反而看清了那两拍各自是什么。

改前（`rx_deserial_design.md` §3）：

> 在 `USB_ERROR` 仍为 1，但字节恢复只看 `st_stat_cur==USB_DATA`——**帧还开 ≠ 还在吐字节**。

改后：

> 这时 `USB_ERROR` 仍为 1，但字节恢复只看 `st_stat_cur==USB_DATA`：帧还开着，不等于还在吐字节。

### 6.4 自检

1. 挑三段读一遍，句式是不是同一个模子：结论 + 破折号 + 加粗短语 + 收尾强调。是就重写。
2. 数密度。先剔掉标题与表格行，再数，最后除以散文千字数：

   ```
   sed 's/^[[:space:]]*[|#].*//' <文件> | grep -o '——' | wc -l
   sed 's/^[[:space:]]*[|#].*//' <文件> | grep -o '\*\*' | wc -l
   ```

**只管新写的文档。** 现有文档一律不动（用户 2026-09-21 明确：现有的不用改，后面的记住这条就行）——
那 432 处破折号留着，不要专门为它开一轮清理。正在写、或本来就因为别的改动要重写的那一节，
顺手按本节写就行。

## 7. 微信公众号兼容（2026-10-08 用户定）

文档要直接粘进微信公众号编辑器发表，公众号的正文渲染器跟 GitHub、Word 都不是一回事，
下面几条是硬约束。§5 的通用格式约定除与本节直接冲突处，仍然有效。
**本节只管今后新写的文档**（与 §6.4 同一口径：存量文档不动，本来就因为别的改动要重写的那一节顺手改）。
本规范文件自身不发布，里面的示例与代码片段不按本节收紧。

### 7.1 图片内嵌，不用超链接

公众号正文里的站外链接和相对路径链接一律点不开（非白名单账号加不了外链），
§5「图用超链接不内嵌」在发公众号的文档里作废。

```markdown
![图 1 PHY 内部模块框图](../fig/phy_block.png)

图 1　PHY 内部模块框图：五个子模块与内部的四根线。
```

- 用内嵌 `![]()`，路径照旧写仓库相对路径；
- 图注写在图的**下一行**（公众号没有 `figcaption`，图注就是正文里的一行字）；
- 粘进公众号编辑器后，每张图要**手动传到素材库**。本地相对路径不会自动上传，想省这一步
  就先让图片有个公网地址再引用；
- 只用 PNG / JPG。`doc/fig/*.svg` 是 graphviz 的中间产物，不引用。

### 7.2 链接一律写成纯文本

超链接会被公众号剥成不可点的文字，跨文档引用改成纯文本：

| 不写 | 改成 |
|---|---|
| `[tx_serial_design.md](tx_serial_design.md)` | `tx_serial_design.md` §2.11 |
| `[bus_state_design.md](bus_state_design.md)` | `bus_state_design.md` |
| `[见 §4.1](#41-xxx)` | 见 §4.1 |

锚点（`#标题`）在公众号里不生效，文档内引用直接写「见 §4.1」。

### 7.3 代码块行宽 ≤ 40 个半角

手机上正文宽度约 345px，代码块按等宽排版，一行只放得下约 40 个半角字符（20 个全角）。
超宽的行不折行，右边会被截掉。

- 命令、伪码过长就手动折行；
- 框图用竖排（一层一行、箭头向下），不要横铺一长排方框；压不下去就出成 PNG，按 §7.1 内嵌。

### 7.4 表格：列数 ≤ 4，一行别超过约 90 个半角

表格在公众号里是横向滚动的，宽表只看得到左边几列；列数一多，连短格也被挤成一字一行。

| 项 | 目标 |
|---|---|
| 列数 | ≤ 4，2~3 列最稳 |
| 一行文本当量 | ≤ 约 90 个半角（中文算 2） |

§5 那条「单元格 ≥120 字符就拆」按公众号口径收紧到上表，两个口径一起来时取严的。

压不下去就拆表；或者把那张表挪回它本来该在的子模块报告里，正文只留一句引用（§5 同一解释只写一处）。

### 7.5 散文一段一行，段内不换行

Markdown 把段落里源码的换行当软换行渲染，可贴进公众号编辑器后，每个换行都变成硬回车，
一段话被从中间劈开，读者看到的是半句一行。所以源码里不要按列宽折行：

- 一个自然段写一整行，长文靠拆段，不靠换行；
- 列表项、引用块同理，续行并回行首那一行；
- 行首带标记的行照旧一行一条（`#` 标题、`|` 表格行、`-` / `1.` 列表项、`>` 引用）；
- 行长只管代码块（§7.3）与表格（§7.4），散文不设上限。

引用块里一行一条独立备注的写法可以留，前提是每行都停在句末；断在句子中间就并回上一行。
首个按此改造的实例仍是 `doc/design_rpt/phy_design.md`（用户 2026-10-10 定）。

### 7.6 不写章节号指路

正文里不要用「见 §4.1」「`tx_serial_design.md` §2.11」「第二章」这种按编号指路。
退一步改成点名子节（「见『关键波形』一节」）也不必要：公众号里没有目录也没有锚点，
告诉读者那节叫什么名字，他一样得从头翻到那儿。本文档内的内容顺着读就到，
直接说方向就行——往后写「见下文」，往回写「见上文」。

| 不写 | 改成 |
|---|---|
| 见 §4.1 | 见下文 |
| 见「关键波形」一节 | 见下文 |
| 见「线状态分类与 driving 门控」 | 见上文 |
| `tx_serial_design.md` §2.11 | `tx_serial_design.md` |
| 《USB 1.1 规范》§7.1.7.1 | 规范里讲连接检测那一节 |

指到别的文档时只写文件名，不写它的小节名（用户 2026-10-08 定）。引用外部标准
（USB 规范、设计指南）保留「讲的是什么」的写法，因为对它们说「下文」没有意义。

两个理由。公众号里章节号对读者没有导航意义，翻不过去；文档一旦离开 Markdown 阅读器
（复制、转 Word、贴微信），编号错位是常事，读者按号找必然找错。

标题里的编号（`## 4. 关键设计点`）保留，它管的是排版层次，不是指路。

### 7.7 其余几条

- 正文里不写 HTML。公众号编辑器会把 `<div>` / `<style>` / `class` 全剥掉，标题和强调一律用
  Markdown 原生语法。
- 不用脚注 `[^1]`，不用 LaTeX `$…$`（公众号不渲染公式，要公式只能出图）。
- 文档第一行的 `#` 是文档名，正文节从 `##` 起，全文只出现这一个 `#`。
  公众号的文章标题在编辑器里另填，正文里不用再写一遍。
- 加粗按 §6.2 的量走。手机上满篇加粗比在 Word 里更花眼。

下面这段一次查两样：代码块与表格的宽度（口径见 §7.3 / §7.4 的「半角当量」），
以及段内换行（一段占了几行就报几行，见 §7.5）。

```python
import sys

def w(s):
    return sum(2 if ord(c) > 0x1100 else 1 for c in s)

def mark(line):
    s = line.lstrip()
    return (s[:1] in ('#', '|', '>') or s[:2] in ('- ', '* ')
            or (s[:2].rstrip('.').isdigit() and s[1:2] == '.'))

lines = open(sys.argv[1], encoding='utf-8').read().split('\n')
inc, para = False, []
def flush(para, end):
    if len(para) > 1:
        print(f'段内换行：行{end - len(para) + 2}..{end + 1} 共 {len(para)} 行')

for i, line in enumerate(lines):
    if line.startswith('`' * 3):
        inc = not inc
        continue
    if inc:
        if w(line) > 40:
            print(f'行{i + 1} 宽{w(line)}')
        continue
    if line.startswith('|') and w(line) > 90:
        print(f'行{i + 1} 宽{w(line)}')
    if line.strip() and not mark(line):
        para.append(line)
    else:
        flush(para, i); para = []
flush(para, len(lines))
```

用法：`python3 <脚本> doc/design_rpt/xxx_design.md`，无输出即合格。
